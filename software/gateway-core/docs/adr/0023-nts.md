# ADR 0023: Authenticated time with NTS

**Status:** Accepted

## Context

The gateway has no RTC; it sets its clock over the network. The clock
decides whether certificates are valid: the HTTPS certificate, EST, and
MQTT brokers checked against a CA (ADR 0020). With plain SNTP anyone on the
path can set it to whatever they like, for example to a time when an
expired or not yet valid certificate is accepted.

Network Time Security (NTS, RFC 8915) authenticates NTP:

1. **NTS-KE**, once in a while: TLS 1.3 to port 4460, ALPN `ntske/1`, the
   server's certificate checked as usual. The client asks for NTPv4 with
   AEAD_AES_SIV_CMAC_256; the server answers with eight cookies and,
   optionally, the NTP server and port to use. Both sides take two keys
   from the TLS exporter (label `EXPORTER-network-time-security`).
2. **NTP with extension fields**, every time the clock is set: a unique
   identifier, one cookie, and an authenticator (AES-SIV with the
   client-to-server key over the packet). The answer echoes the identifier,
   is authenticated with the server-to-client key, and brings fresh
   cookies, encrypted. A cookie is used once; the server keeps no state.

Public servers: PTB (`ptbtime1-3.ptb.de`), Netnod (`nts.netnod.se`),
time.nl, Cloudflare; chrony serves NTS with a certificate of its own.

## Decision

**A time server set as `nts://host[:port]` is asked with NTS**
(`ntp-server`, `PATCH /api/v1/tls` `ntp_server`, the HTTPS page). A plain
name stays plain SNTP, as do the DHCPv6 server and the `pool.ntp.org`
default. Without a working key exchange there is no fallback to plain NTP
for an NTS server: the point is not to trust unauthenticated time.

- **Wire formats** in `gateway-core/src/nts.rs` (pure, host-tested): KE
  records, the request with placeholders for as many fresh cookies as are
  missing, the answer's checks, AES-SIV from RustCrypto's `aes-siv` 0.7
  (it shares `aes`, `ctr` and `cipher` with embedded-tls' AES-GCM).
- **TLS** with embedded-tls, as for MQTT. It had no exporter: the
  Th3Link fork adds `export_keying_material` (RFC 8446 7.5), tested against
  rustls; meant to go upstream (`software/patches/README.md`).
- **The server's certificate** is checked against the trusted CAs and the
  host name with `tls::verify_chain`, like an MQTT broker's, but only after
  the key exchange: chrony gives a whole NTS-KE session 2 s from the
  connection on, and checking a P-384 chain (Let's Encrypt's Gen Y) takes
  1.2 s here. During the handshake the server still has to prove it holds
  the certificate's key (CertificateVerify). Nothing it sent is used before
  the chain is accepted.
- **The first time**: before the clock is set, the chain is checked at the
  firmware's build time, and a certificate only has to be unexpired then
  (`tls::Dates::NowOrBuildTime`), like chrony's `nocerttimecheck`. From the
  first authenticated answer on, the real time counts.
- **When**: the key exchange runs when there are no cookies, when the
  server sends an NTS NAK, after four requests in a row without an
  authenticated answer, and when the setting changes. It shares the one TLS
  slot with the web server and EST (~25 KB of heap while it runs). NTP
  is asked every six hours, as before.
- **Status**: `GET /tls` `time_authenticated` and `nts` (cookies, last key
  exchange, last answer, last error); `tls-status` and `network` on the
  console; the HTTPS page.

## Consequences

- With an `nts://` server, the certificate checks rest on authenticated
  time. A man in the middle can only withhold it.
- A key exchange costs a TLS handshake and a chain check (about 2 s) once
  per boot and whenever the cookies run out; an NTS request is ~230 bytes
  instead of 48.
- 1.6 KB more static RAM (cookies, keys), and the flash for AES-SIV.
- The cookies and keys aren't kept across restarts: every boot starts with
  a key exchange.
- Cloudflare's certificate is issued by SSL.com, which isn't built in: it
  has to be installed as a trusted CA first.
